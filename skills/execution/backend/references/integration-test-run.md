# run 执行规则

## 1. 读取项目事实

执行任何测试前，先只读检查：

1. 仓库根目录的 `AGENTS.md`、README、开发规范和测试说明。
2. [integration-test-stack.md](./integration-test-stack.md)，以及仓库中的 manifest、构建文件、Makefile / Taskfile、CI 配置、测试脚本和环境示例。
3. 已有测试文件、测试运行器配置、测试标签 / 分组、测试目录及辅助代码。
4. 路由注册、Handler / Controller / Route / Resolver / RPC 入口、业务层、数据访问层以及相关外部依赖。
5. 当前分支、工作区状态、语言 / 框架 / 测试运行器、测试层级、测试环境标识和可用测试命令。

只读取与当前范围判定相关的文件，不为寻找更多测试而无边界扫描整个仓库。

如果确认范围内没有可执行的已有接口测试，输出缺失接口、建议测试文件和建议的 `$backend integration-test generate [scope]` 命令后停止。`run` 不得创建或修改测试代码。

## 2. 解析用户指定范围

用户提供接口、包、测试文件或测试名称时：

1. 校验目标在仓库中真实存在。
2. 将接口追踪到路由与项目原生入口，再映射到已有接口测试。
3. 将包、文件或测试名称解析为最小可执行命令。
4. 多个目标取并集，但不得增加用户未指定的相邻包或全仓测试。
5. 向用户简要说明实际命令、环境和输出报告路径。

用户显式要求运行测试已构成范围授权。只有目标不明确、环境不安全、命令会产生额外外部影响或需要扩大范围时才再次等待确认。

## 3. 自动识别变更范围

用户未提供 scope 时，按以下顺序识别：

### 3.1 确定比较基准

比较基准优先级：

1. 用户指定的 base 分支或 Commit。
2. PR / MR、CI 或仓库说明中明确的目标分支。
3. 仓库可验证的默认目标分支及其 merge-base。

工作区未提交和已暂存变更必须一并纳入。无法可靠确定分支比较基准时，先说明已知 Git 状态并请用户指定，不得擅自选择 `main`、`master` 或 `daily`。

### 3.2 建立变更到测试的证据链

依次检查：

1. 变更是否直接发生在已有集成测试或测试 fixture。
2. 变更符号被哪些路由、Handler / Controller / Route / Resolver 或 RPC 入口调用。
3. 受影响入口依赖哪些业务组件、数据访问组件、缓存或消息流程。
4. 哪些已有测试直接调用对应入口、共享测试夹具或同一业务流程。
5. 仓库现有测试命令、测试标签 / 分组 / feature 和环境约束是否允许最小执行。

候选测试必须有源码证据。只有目录相邻或名称相似但没有调用、路由或业务关联证据时，标记为“低置信候选”，不能直接列入默认执行范围。

### 3.3 生成待确认清单

向用户展示：

| 候选 | 代码变更 | 受影响接口 | 测试目标 | 拟执行命令 | 选择理由 | 置信度 |
|---|---|---|---|---|---|---|
| T-01 | `<file:line>` | `<method path>` | `<module / test>` | `<command>` | `<evidence>` | 高 / 中 / 低 |

同时说明：

- 比较基准和纳入的工作区变更。
- 未找到对应测试的接口。
- 因共享路由、中间件、鉴权或基础设施变更而建议扩大的范围。
- 计划生成的报告路径。

展示后停止，不执行测试、不启动服务、不创建报告。等待用户明确确认、增加、删除或修改测试。

### 3.4 确认后防漂移

执行前重新读取 Git 状态与相关 diff：

- 无变化：使用用户确认后的最终范围。
- 有新增或修改：说明范围变化，重新生成受影响候选并再次确认。
- 只有无关文件变化：说明判断依据；仍不得静默加入测试。

## 4. 执行前检查

1. 确认目标不是生产环境。
2. 确认测试命令来自仓库事实或用户指定。
3. 确认测试所需依赖已经可用；缺失时停止，不自动安装或启动共享服务。
4. 确认命令不会运行超出授权范围的包或测试。
5. 记录开始时间、分支、Commit、工作区状态、语言 / 框架 / 测试运行器、测试层级和最终范围。

任何语言都优先使用项目现有脚本、wrapper 或 CI 已验证命令。只有仓库没有封装命令，且运行器、工作目录和范围都能可靠映射时，才组合 runner 的最小原生命令。命令形状必须来自 [integration-test-stack.md](./integration-test-stack.md) 要求的仓库证据，不直接套用示例。

如仓库已有测试标签 / 分组、feature、环境变量或超时参数，必须沿用真实配置，不得自行省略或开启。

## 5. 执行与结果收集

执行时记录：

- 完整测试命令和工作目录。
- 开始、结束时间及总耗时。
- 测试模块 / 工程 / 套件、测试用例和嵌套用例。
- 通过、失败、阻塞和跳过状态。
- 与失败直接相关的脱敏日志摘要。

不得自动重试。用户明确要求重试时，首次结果和重试结果都写入执行明细。

结果分类：

- 编译失败、依赖不可用、认证失败、无法连接测试基础设施：`阻塞`。
- 测试已运行且断言失败：`失败`。
- 框架明确 skip：`跳过`。
- 目标断言全部通过：`通过`。

## 6. 生成报告

使用 `../templates/backend-integration-test-report.md`，要求：

1. 不删除任何一级标题；无内容写“无”。
2. 只写实际读取或执行得到的事实。
3. 范围与边界必须说明“测了什么”和“实际断言验证了什么”。
4. 记录语言、框架、测试运行器和每类用例的真实测试层级，不把使用 fake / mock 的入口测试包装为组件集成测试。
5. 失败用例的遗留问题栏写“待转遗留问题”，除非用户已经提供真实编号或链接。
6. 不加入截图、覆盖率、Postman、Apipost、Apifox 或其他人工证据章节。
7. 报告总数必须与执行明细一致。
8. 报告写入前检查同名文件；存在时请用户决定新路径或是否覆盖。
9. 测试由 `generate` 新增时，在范围来源和测试文件中标明“人工确认后生成”。
