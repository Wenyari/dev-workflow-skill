# generate 生成规则

## 1. 定位

`generate` 用于接口实现已经存在、但对应接口层集成测试缺失或不完整的场景。它生成或补充项目原生测试代码，并运行经过用户确认的最小验证。

本命令默认生成 Handler / Controller / HTTP 或 RPC 入口层测试。除非用户明确扩大范围，否则不生成 Service、Repository、数据库、性能或端到端环境测试。

## 2. 读取事实与确认期望

生成测试前必须读取：

1. 用户指定接口，或按 `integration-test-run.md` 的自动识别规则得到的受影响接口。
2. 路由注册、Handler / Controller、请求 DTO、响应 DTO、错误映射和权限中间件。
3. 同包及相邻模块已有的接口测试、fake、fixture、helper 和命名风格。
4. 仓库已有测试命令、build tag、环境变量和 CI 配置。
5. 用户提供的 API 契约、PRD 或技术方案；没有文档时只使用能从代码和现有约定验证的事实。

期望值来源优先级：

1. 用户明确确认的接口契约或验收标准。
2. 已审核 API 文档、PRD 或技术方案。
3. 仓库内稳定的公共响应、错误码和同类接口约定。
4. 当前生产代码行为，仅用于回归性机械事实，不用于臆造业务期望。

文档、现有测试和实现互相冲突时，列为阻塞待确认。不得自行选择一个版本生成断言。

## 3. 识别测试缺口

为确认范围内的接口建立覆盖矩阵：

| 接口 | 已有测试 | 缺失场景 | 建议文件 | 依据 |
|---|---|---|---|---|
| `<METHOD /path>` | `<tests or 无>` | `<cases>` | `<file>` | `<contract / code evidence>` |

按接口实际行为选择用例，不机械凑数。通常检查：

- 正常请求和关键响应字段。
- 必填、格式、枚举、分页或边界参数校验。
- 鉴权与权限分支，仅在项目测试设施能可靠模拟时生成。
- 未找到、重复、状态非法、乐观锁冲突等已定义业务错误。
- 创建、更新、状态变更后的关键返回元数据。
- 敏感字段不返回、脱敏或仅按权限返回。

如果测试只能通过调用真实生产或共享环境完成，停止生成并说明原因，不写带真实凭据或外部副作用的测试。

## 4. 写入前确认门槛

写文件前必须向用户展示：

| 文件 | 操作 | 接口 | 拟生成用例 | fake / fixture | 验证命令 |
|---|---|---|---|---|---|
| `<path>` | 新增 / 修改 | `<interface>` | `<test names and scenarios>` | `<dependencies>` | `<command>` |

同时说明：

- 每条断言的事实来源。
- 不会修改的生产文件。
- 测试是否使用 fake，哪些真实副作用因此不在验证范围。
- 生成后要运行的最小测试命令和报告路径。

展示后停止。只有用户明确确认该文件与用例计划后才能写入。用户可以删除、增加或修改用例；确认范围以用户最后回复为准。

## 5. 测试代码生成规则

- 只新增或修改确认过的测试文件。
- 优先在既有测试文件中补充同一接口场景；文件不存在时按项目命名和目录惯例创建 `*_test.go`。
- 复用现有 package、router helper、fake UseCase、fixture 和断言风格。
- 测试名称必须表达入口、场景和预期，不使用 `TestCase1` 等无语义名称。
- 测试必须可重复、相互隔离，不依赖执行顺序、当前时间、随机外部数据或共享生产资源。
- 请求与响应样例不得包含真实 Token、密码、Cookie 或用户敏感数据。
- 不新增第三方测试依赖，不修改 `go.mod` / `go.sum`，除非用户另行明确确认。
- 不修改生产代码来迁就测试，也不复制大量生产逻辑到测试中计算期望值。

## 6. 格式化与验证

写入后：

1. 只格式化确认过的测试文件，例如 `gofmt -w <test-files>`。
2. 检查 Git diff，确认没有生产文件或无关测试变化。
3. 按确认计划运行最小测试命令，不扩大到全仓测试。
4. 使用 `integration-test-run.md` 的结果口径生成报告。

编译失败时先判断原因：

- 生成代码的 import、类型、fake 或语法错误：只修复确认过的测试文件，再运行一次最小验证。
- 依赖或环境问题：标记阻塞，不修改环境或生产代码规避。

断言失败时：

- 断言有明确契约依据：保留失败，不能把期望值改成当前实现结果。
- 断言依据不充分：停止并向用户说明不确定项，不能为了通过而猜测。
- 不自动修改 Handler、Service、Repository 或其他生产实现。

## 7. 交付

最终回复和报告必须列出：

- 新增或修改的测试文件。
- 新增用例及其对应接口。
- 实际运行命令和结果。
- 使用的 fake / fixture 与未验证的真实副作用。
- 失败、阻塞及待转遗留问题。
