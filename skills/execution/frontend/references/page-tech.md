# page-tech 子命令

`page-tech` 用于产出页面级前端技术方案。方案只回答页面如何落到代码、依赖哪些接口和现有资源、有哪些阻塞实现的问题。

它不是需求复述、用户操作说明、自测清单、验收标准、仓库调研报告、项目入门说明或完整文件改动清单。

执行 admin-fe 页面方案时，必须读取或内化项目根目录的
`ADMIN_FE_WORKFLOW.md`。页面方案不得违反 admin-fe 的路由、请求、状态、Wujie、UI 复用和验证规则。

## 工作流程

1. 识别页面类型：列表页、详情页、表单页、配置页、工作台、弹窗/抽屉页面、混合页面。
2. 从用户请求、需求资料、设计稿、接口资料和当前仓库中收集上下文。
3. 判断每个章节的上下文是否足够。
4. 必需上下文缺失时，向用户确认，或写入“风险与待确认项”。
5. 只有在需要确认路径、可复用资源、UI 库用法、状态模式、接口封装、相似页面时，才读取仓库代码。
6. 使用 `../templates/page-tech.md` 作为文档骨架。
7. 页面不涉及的条件章节写“不涉及”，不要强行展开。
8. 完整读取 `mermaid.md`，判断哪些内容需要配图，先生成并检查 Mermaid 源码；需要飞书落地时只调用当前环境实际可用的飞书文档或画板能力。

如果用户要求最终发布到飞书，先生成完整 Markdown，再交给
`tools/lark/scripts/lark_publish_doc.mjs`。不要一边写方案一边拼飞书 blocks。

## 编写原则

- 并列内容默认使用无序列表；只有存在明确顺序、流程或优先级时才使用有序列表。
- “功能列表”和“接口清单”不要重复。页面技术方案必须优先写成“功能与接口映射”表格，在同一行说明功能、PRD 交互项、接口、输入参数、响应数据、展示形式、状态变化、刷新行为和异常反馈。
- “功能与接口映射”不得用纯 bullet 替代表格，除非页面完全不依赖接口；如果确实不依赖接口，必须在该章节说明原因。
- “目录结构与产物路径”使用树形代码块，不使用表格。
- “可复用资源清单”优先使用树形代码块展示真实路径，再用短句补充用途。
- “组件拆分”命中 `mermaid.md` 的组件边界配图条件时，使用 `flowchart LR` 表达。节点内可以写 UI 资源、复用资源和接口资源，但不要把每个资源拆成独立资源节点。
- 节点文本控制在 3 行左右；资源较多时用顿号分隔，避免图过宽和分叉过多。

## 仓库证据

存在前端仓库时，以下内容必须基于真实代码：

- 目录结构与预期产物路径
- 可复用公共组件和业务组件
- hooks、utils、constants、services、stores/models
- 项目当前使用的 UI 库组件
- 路由、请求封装和状态管理方式

仓库不可用时，不得写具体路径，也不得声称存在某个可复用资源。可以描述预期职责，但必须将具体落点列为待确认。

admin-fe 必须遵守：

- 路由目录是 `src/routes/`。
- 禁止手动编辑 `src/routeTree.gen.ts`。
- API 调用统一使用 `src/services/request.ts`。
- 页面临时状态不使用 Zustand。
- shell 状态使用 `src/stores/shell-store.ts`。
- Wujie 逻辑复用 `src/shared/wujie-bridge.ts`。
- UI 复用顺序：Apex UI → `src/common` → 业务局部组件 → 新建局部组件。

## 外部资料

用户提供飞书云文档链接作为需求、设计或接口来源时，必须先使用
`lark-read` 读取文档。读取失败时，停止依赖该文档生成方案，不根据链接标题、URL 或用户转述猜测内容。

只在产品规范会直接影响字段类型、请求参数、校验规则或组件选型时读取对应规范。不要为了补充 UI、自测或异常场景而加载无关规范。

资料发生冲突时不得自行取舍，必须在“风险与待确认项”中写明冲突事实、实现影响和确认对象。

## 非功能性需求推荐

先判断页面是否存在实际工程压力，再向用户给出明确建议：

- 数据量大、高频刷新、实时数据、复杂上传或高成本渲染：建议补充性能要求。
- 涉及敏感数据、权限差异、危险操作或外部访问：建议补充权限与安全要求。
- 明确覆盖多终端、外部用户或特定浏览器环境：建议补充响应式、可访问性或兼容要求。
- 普通内部页面且项目已有统一规范：建议不增加页面级非功能性要求，沿用项目现状。

不得只问“是否需要非功能性需求”。询问时必须同时给出推荐、判断依据和需要用户确认的具体项目。

用户已经明确提出要求时，不重复询问；直接记录已确认结论。用户未确认时暂停完成方案，不替用户选择“需要”或“不需要”。

## 埋点与监控推荐

分别判断埋点和监控，不把两者混为一个结论：

- 页面承担关键转化、重要业务结果、流程完成率或新功能效果验证：建议增加埋点。
- 页面包含关键接口、提交链路、资金或权限操作、重要错误：建议增加专项监控。
- 项目已有全局错误监控且页面没有特殊业务指标：建议不新增页面级监控。
- 页面没有产品分析目标：建议不新增埋点。

不得臆造事件名、指标阈值、监控面板或告警规则。用户确认需要后，只记录已知要求；具体定义仍不明确时进入待确认项。

## 图表策略

鼓励使用图表表达复杂技术关系，先选择方向和层级，再填写节点：

- 页面区域和上下层级：优先使用 `flowchart TB`。
- 组件关系和同层模块：优先使用 `flowchart LR`。
- 多接口调用顺序和刷新依赖：优先使用 `sequenceDiagram`；需要同时展示数据落点时使用 `flowchart LR`。
- 多个业务状态之间的转换：使用 `stateDiagram-v2` 并声明 `direction LR` 或 `direction TB`。

页面技术方案中的图必须帮助审核者理解方案，不做装饰。执行本节规则时完整读取 `mermaid.md`，按其中的选图矩阵、单图交付契约、模板替换规则和飞书降级方式生成图。

- 一张图只表达一个主题，主链路保持单一方向。
- 使用 `subgraph` 对页面层、状态层、接口层或数据层分组。
- 主链路按阅读方向排列，分支靠近所属节点，避免长距离回连和交叉。
- 同一层节点使用相同形状和尺寸，节点文案控制在两到三行。
- 复杂图拆为组件关系、数据流或状态流转等多张图。

颜色规则：

| 语义 | 填充色 | 描边色 |
| ---- | ------ | ------ |
| 入口、输入 | `#E8F1FF` | `#3B82F6` |
| 页面组件、处理过程 | `#F3E8FF` | `#8B5CF6` |
| 接口、外部依赖 | `#E6FFFB` | `#0F766E` |
| 数据、状态 | `#F3F4F6` | `#64748B` |
| 成功结果 | `#ECFDF3` | `#22C55E` |
| 风险、待确认 | `#FFF7E6` | `#F59E0B` |
| 错误、阻塞 | `#FEF2F2` | `#EF4444` |

- `flowchart` 和 `stateDiagram-v2` 使用 `classDef` 定义颜色，并使用 `class` 或 `:::` 将语义类绑定到节点。
- `sequenceDiagram` 不支持 `classDef`，使用初始化主题统一基础配色，必要时用 `rect rgb(...)` 标记成功、风险或错误片段。
- 同一语义在全文保持相同颜色，不使用无意义的随机配色。

简单列表、单接口页面、线性数据流和普通组件树使用文字、列表或表格即可。不得为了增加文档篇幅重复表达同一内容。

- 组件层级超过 5 个主要模块：画组件关系图。
- 异常处理分支较多：画异常处理流程图。
- 页面与上游/下游页面联动较多：画页面跳转流程图。
- 前端持有规范化实体缓存且关系复杂：可以画 ER 图；只描述后端数据库关系时不画。

## 交付前检查

以下情况不要画图：

- 只有简单列表展示、流程少于 4 步，且未命中任何必画条件。
- 图只能重复正文，没有增加理解价值。
- 上下文不足，图只能靠猜。
- 只是为了让文档看起来丰富。

### 选图、交付与飞书落地

- 根据 `mermaid.md` 中的“评审问题—图型”矩阵选择图型，不按章节机械配图。
- 每张图都必须包含非空的“图示目标”和至少一条“关键结论 / 不变量”。
- `5.6 数据流` 保留模板中的默认示例图；正式方案必须替换为当前页面的真实节点和关系，不得原样交付。
- 不命中任何必画条件时，可以删除默认示例图并填写非空的“无需配图原因”；有图和无需配图原因只能二选一。
- 文档中保留 Mermaid 源码。用户要求飞书交付时，只使用当前环境实际可用的飞书文档或画板能力；没有可用渲染能力时保留源码并明确“未渲染”，不得调用不存在的工具或声称已生成图片。

## 章节规则

### 1. 背景与目标

必需上下文：

- 页面名称
- 所属业务模块或功能域
- 需求描述、PRD、设计说明或用户给出的页面目标

写作规则：

- 只写这个页面要解决的问题和页面级目标。
- 不写项目背景，不写技术栈。
- 如果目标只能从设计稿推断，必须标注“根据设计稿推断，需确认”。

### 2. 页面范围

必需上下文：

- 页面入口或导航来源
- 设计稿或需求中的页面区域
- 页面状态
- 非目标范围或明确的需求边界

写作规则：

- “页面入口”写用户从哪里进入页面，不写路由实现。
- “页面结构”写用户可见区域，不写组件名称。
- “页面状态”至少考虑正常、loading、空数据、失败、无权限。
- “非目标范围”必须存在；如果用户未提供，可以提出建议边界，但必须标记为待确认。

### 3. 需求拆解

必需上下文：

- 功能需求
- 用户操作路径
- 交互规则
- 接口路径、入参、响应数据和展示形式，如果页面功能依赖接口。

写作规则：

- 功能列表只写页面内功能，并必须优先写成“功能与接口映射”表格。
- 如果功能依赖接口，在同一行内说明 PRD 交互项、接口、输入参数、响应数据、展示形式、状态变化、成功后的刷新范围和异常反馈。
- 建议表头为：功能、PRD 交互项、接口、入参、响应数据、页面展示 / 行为、状态变化、成功后刷新、异常反馈。
- 不再单独重复一份纯接口清单，除非用户明确要求接口评审表。
- 用户流程写用户动作链路。
- 关键交互写触发条件、系统行为和反馈结果。
- 关键交互必须覆盖 PRD 交互清单，不能只写通用查询、保存、删除。
- 不写开发步骤。
- 关键交互不明确时，列入待确认，不要补全规则。

### 4. 数据与接口

必需上下文：

- 页面展示字段、依赖数据或接口文档
- 已有 service 文件、mock 数据或后端约定

写作规则：

- 只有用户提供或代码中存在时，才写真实接口名称、路径、方法、参数和响应字段。
- 接口未确认时，可以写预期数据依赖，但接口细节必须标记为“待后端确认”。
- 不得凭空生成 TypeScript 请求类型或响应类型。
- 异常处理写页面表现，不写底层请求封装设计。
- 如果 `3.1 功能与接口映射`
  已完整覆盖接口，本章只补充公共数据依赖、参数约定、响应约定和异常口径，避免重复。

### 5. 前端实现方案

必需上下文：

- 可访问的前端仓库，用于确认路径和可复用资源
- 页面结构所需的设计或需求上下文
- 项目当前实际使用的 UI 库

写作规则：

- “目录结构与产物路径”只列页面级主要预期产物，不写完整文件改动清单。
- “目录结构与产物路径”使用树形代码块。
- “可复用资源清单”必须来自已有代码，可包含组件、hooks、utils、constants、services、stores/models、业务组件。
- “可复用资源清单”优先使用树形代码块展示路径。
- “UI 库组件清单”必须匹配项目当前实际使用的 UI 库。
- “组件拆分”基于页面区域和复用资源，不要过度拆分。
- “组件拆分”涉及多个区域，且跨组件共享状态、事件或所有权边界需要评审时，优先提供 `flowchart LR` 组件关系图，并在组件节点内压缩标注 UI 库资源、复用资源和接口资源。
- “状态设计”按需覆盖请求状态、页面状态、选中状态、表单状态、业务状态。
- “数据流”描述数据从入口参数、接口、用户操作到 UI 和提交的流转。
- 数据来自 2 个及以上接口，或存在创建 / 编辑 / 删除后刷新多个查询的联动时，“数据流”必须包含 Mermaid 数据流转图。
- 如果提交链路包含前端校验、接口提交、结果刷新和错误回填，必须在“数据流”或“提交表单与校验”中补充提交流程时序图。
- “提交表单与校验”是条件章节；纯展示页、列表页、只读详情页写“不涉及”。

### 6. UI 与体验约束

必需上下文：

- 设计稿来源或明确 UI 要求
- 终端范围，例如只支持桌面端或需要响应式

写作规则：

- 明确设计信息来源。
- 涉及异步数据的页面，必须写 loading、空状态和错误反馈。
- 没有响应式要求时，遵循项目既有适配方式，不新增断点假设。
- 不写笼统的视觉形容词。

### 7. 非功能性设计

必写：

- 性能设计
- 权限与安全
- 可维护性
- 可测试性

条件写：

- 可访问性：项目或页面有明确要求时写。
- 埋点与监控：存在埋点、日志、监控或分析上下文时写。

写作规则：

- 只写和当前页面相关的内容。
- 不得臆想性能指标、埋点事件名、监控面板或权限码。
- 性能设计重点关注分页、防重复请求、缓存、懒加载、大列表渲染、避免高成本重复渲染。
- 权限与安全重点关注页面访问权限、操作权限、敏感字段、危险操作确认和错误信息暴露。

### 8. 边界场景

必需上下文：

- 需求和数据行为
- 已知接口与权限行为

写作规则：

- 覆盖真实可能发生的页面边界：空数据、请求失败、无权限、重复提交、字段缺失、长文本、数据过期、部分数据缺失。
- 不写和页面无关的理论异常。

### 9. 完成标准

必需上下文：

- 页面目标
- 功能范围
- 设计和接口预期

写作规则：

- 保持简短。
- 说明页面做到什么程度算完成。
- 不写详细测试用例，不写 coding 排期。

### 10. 风险与待确认项

必写。

写作规则：

- 收敛前面所有不确定信息。
- 单独收敛 PRD / 接口 / 仓库代码 / 产品设计规范之间的冲突项。
- 每个问题都要具体到可以直接问产品、设计、后端或前端负责人。
- 如果没有不确定项，只有在确认全文没有臆想内容后，才写“暂无明确待确认项”。

## 交付前自检

生成页面技术方案后，必须执行一次人工自检；如果已经落地为 Markdown 文件，优先运行：

```bash
node <agent-root>/skills/execution/frontend/scripts/check_page_tech_doc.mjs <markdown-file>
```

人工复核：

- 是否按模板章节规则完成五个核心章节。
- 功能与接口表是否覆盖页面能力、真实接口、关键数据和刷新关系。
- 路径、复用资源、UI 库和状态方案是否有仓库证据。
- 表单可选字段是否包含类型判断和空值归一化。
- 是否针对非功能性需求、埋点和监控给出有依据的推荐并取得用户确认。
- 复杂关系是否选择了合适的图表，简单关系是否避免重复表达。
- 所有冲突和关键缺失信息是否进入风险与待确认项。
