# workload-plan 子命令

`workload-plan` 用于在开发排期前，根据 PRD、UI、API 契约和目标仓库事实，生成前端工作量拆分报告。报告只评估内容规模、复杂度、并行开发链路、耦合点、交付里程碑和阻塞项，不代替开发负责人填写工时。

## 1. 输入

| 输入 | 要求 |
| --- | --- |
| PRD | 必需；飞书链接先通过共享飞书能力完整读取 |
| 目标前端仓库 | 必需；读取仓库规范和用户指定的标准参考模块 |
| API 契约 | 优先读取 Apifox/OpenAPI，其次读取后端仓库和现有 Service；缺失时记录为“未发现” |
| UI | Figma、正式设计稿或用户明确认可的等价 UI；HTML 原型默认只算参考材料 |
| PRD Review | 有则读取，用于识别阻塞项和范围冲突 |
| 用户范围约束 | 包括本期/非本期、参考模块、禁止参考模块和输出路径 |

不要因 API 或 UI 缺失而拒绝生成报告；缺失事实必须进入总体规模、里程碑前置状态和阻塞项。

## 2. 证据优先级

1. PRD 决定业务范围和规则。
2. API 契约决定可用接口和数据结构，不反向补造业务需求。
3. 正式 UI 决定页面视觉、布局和交互状态。
4. HTML 原型只用于识别交互形态，除非用户明确认可其为定稿。
5. 目标仓库决定真实复用能力、目录结构、权限、隐私和技术约束。
6. 用户指定的标准模块优先于其他业务模块。

每个结论都要能指向实际文档、设计节点、API、代码或用户确认，禁止凭经验把未发现写成已就绪。

## 3. 分析流程

### 3.1 盘点范围

从 PRD 提取全部本期待开发项，至少包含：

- Page。
- Drawer。
- Modal 和确认弹层。
- 表单和动态编辑器。
- 主表、子表和批量操作。
- Route、Service、Query、Permission、Privacy、i18n 和 Shared。
- 上传、导入、导出、下载和异步同步。
- 状态变化、金额计算和跨模块回写。

为每项标记唯一去向：

- 纳入开发。
- 复用已有实现。
- 暂缓。
- 阻塞。
- 明确不属于本期。

本期需求不得存在未分类项。内部建立以下追踪关系，不要求把完整矩阵写入最终报告：

```text
PRD 条目
→ 页面或基础建设
→ 组件/Service/Permission
→ UI 证据
→ API 证据
→ 开发线
→ 交付里程碑
```

### 3.2 检查 API 契约

逐项检查：

- 接口方法和路径。
- 请求参数。
- 响应结构。
- 分页、筛选和排序。
- 状态枚举和节点枚举。
- 权限字段或 `can` 结构。
- 批量接口及部分失败语义。
- 上传、导入、导出和下载。
- 错误码和错误消息。
- 并发、幂等和重复提交。

API 状态只能使用：

- 已完整。
- 部分完整。
- 未发现。
- 不需要 API。

统计 API 完整度时以页面或独立业务域为分母，并在总体规模中写出具体数字。

### 3.3 检查 UI 完整度

逐页面检查：

- 列表默认态。
- Drawer 和各 Tab。
- Modal 和表单。
- Loading、Empty 和 Error。
- 编辑、禁用和权限状态。
- 状态切换和确认反馈。
- 批量操作。
- 未保存退出。
- 上传、导入、导出和异常反馈。

UI 状态只能使用：

- 已完整。
- 部分完整。
- 未提供。
- 不需要独立 UI。

只有正式设计稿或用户明确认可的等价稿件可以标记为“已完整”。单独的 HTML 参考原型默认标记为“部分完整”。

### 3.4 评估复杂度

| 复杂度 | 判断标准 |
| --- | --- |
| 低 | 纯展示、简单确认、无复杂状态联动 |
| 中 | 查询分页、筛选排序、普通表单或单模块权限 |
| 高 | 动态表单、异步选项、批量操作、多接口或跨组件状态 |
| 很高 | 金额计算、父子数据、跨模块状态机、并发占用或结果回写 |

API 或 UI 缺失不改变组件自身技术复杂度，但必须提高交付风险并进入前置状态或阻塞项。

### 3.5 拆并行开发线

- 最多生成 5 条独立开发线。
- 每条开发线最多 10 个横向模块或关键组件。
- 优先按独立数据域拆线，不按文件目录机械拆线。
- 用虚线或独立节点标出跨线依赖和耦合点。
- 明确哪些内容可以完全并行、只能开发结构、必须等待上游契约。

第三章必须使用 `flowchart LR` 和 `subgraph`，不要使用 `sequenceDiagram`。

### 3.6 生成交付里程碑

里程碑由真实依赖倒推，不使用固定阶段：

- API 和 UI 已完整：可以安排完整业务交付。
- API 部分完整：只安排契约已明确部分。
- UI 部分完整：只安排结构和明确交互。
- 上游数据模型未稳定：下游不能列为完整交付。
- 阻塞项未解除：必须写入里程碑“前置状态”。

里程碑表格固定为：

| 里程碑 | 交付内容 | 前置状态 | 单人工时评估 |
| --- | --- | --- | --- |

“交付内容”必须同时写明 Page、Drawer、Modal、其他开发单元的数量、主要范围和复杂度。“单人工时评估”由用户填写，生成时保持空白。

不要添加“验收条件”和“联调对象”列。

### 3.7 生成阻塞项

阻塞项必须来自实际证据，重点检查：

- API 契约缺失或冲突。
- UI 未完整就绪。
- PRD 状态机、金额公式或字段口径缺失。
- Permission、Privacy 和数据范围缺失。
- 批量、文件、导入导出和异常规则缺失。
- 本期待开发项是否全部覆盖。

没有阻塞项时明确写“当前未发现阻塞项”，不要补造问题。

## 4. 输出

使用 [../templates/workload-plan.md](../templates/workload-plan.md) 作为固定骨架。默认输出到用户确认的文档目录，文件名为 `workload-plan.md`；用户指定中文文件名或既有路径时采用用户路径。

报告只保留五章：

1. 总体规模。
2. 功能拆分。
3. 开发链路。
4. 交付里程碑。
5. 前置确认与阻塞项。

生成后运行：

```bash
node skills/execution/frontend/scripts/check_workload_plan_doc.mjs <报告路径>
```

静态检查通过不代表语义分析正确；必须人工复核需求覆盖、API/UI 证据、组件计数和耦合关系。

## 5. 明确不做

- 不填写具体人日、小时、周数或人员排期。
- 不输出全量文件目录树。
- 不逐文件描述实现细节。
- 不把原型内容补进 PRD。
- 不把缺失 API 写成假设接口。
- 不把缺失 UI 写成已就绪。
- 不修改业务代码。
